## v1.8.0 — Единый Pi Agent Harness и профессиональное ядро создания

InkOS 1.8.0 сводит Chat Agent и все производственные конвейеры в один harness вокруг pi-agent. Модели понимают, предлагают и вызывают возможности; InkOS отвечает за подтверждение, контекст, состояние, атомарное сохранение и достоверность артефактов. Длинные романы, короткие рассказы, сценарии, раскадровки, интерактивные фильмы, Play и перевод сохраняют свои ремесленные методы, разделяя инфраструктуру выполнения, поиска, наблюдения и восстановления.

- **Настройка моделей**: Studio включает настройки провайдеров, роутинг моделей, настройки сервиса обложек, агрегаторы [kkaiapi](https://en.kkaiapi.com/) / OpenRouter и пользовательские OpenAI-совместимые эндпоинты.
- **Один производственный harness**: Studio Chat, TUI, `inkos interact` и production-воркеры разделяют инструментальный цикл pi-agent и типизированную границу action/result. Существующие конвейеры — детерминированные, прерываемые возможности, а не параллельные движки принятия решений на естественном языке.
- **15 встроенных профессиональных Skills**: отдельные пакеты `SKILL.md` покрывают написание/рецензию длинных текстов, коммерческие короткие рассказы, Play, сценарии, раскадровки, интерактивное кино, перевод, разбор, рыночные исследования, импорт, обложки и семантическое «очищение от AI». Каждый формат разделяет архитектуру Skill, а не промпты, специфичные для длинных текстов.
- **Единый локальный поиск**: память истории, архивные материалы и справочные ссылки Skill используют одну восстанавливаемую проекцию SQLite FTS5 / BM25. Исходные файлы остаются авторитетными, а найденные доказательства сохраняют указатели на источник.
- **Связанные с книгой референсы**: импортированные материалы можно явно привязать к книге с указанием целей использования, и тогда они извлекаются по задаче, а не вливаются в контекст целиком.
- **Безопасные рабочие зоны глав**: проза, состояние, крючки и снапшоты прогонов проверяются в рабочей зоне главы и атомарно фиксируются, чтобы состояние не продвигалось при сбое сохранения прозы.
- **Согласованность между форматами**: Short, сценарии, раскадровки, интерактивное кино, Play и перевод разделяют снапшоты, привязку Skill, наблюдения длины, отмену и восстановление, сохраняя специфичные для формата состояние и ремесло.
- **Более надёжные длинные задачи**: многоглавие написание выполняется последовательно как одна восстанавливаемая задача; дедлайны первого токена и простоя потока, ремонт устаревшего состояния и атомарные наборы файлов снижают пассивные зависания и частичные завершения.
- **TUI на уровне Studio**: явные поверхности `/new`, `/short`, `/play`, `/cover`, `/write`; структурированные `/confirm` / `/cancel`; сессионный `/model`; адаптивная светлая/тёмная палитра терминала. Обычный свободный текст по-прежнему отдаётся Agent.
- **Модели и рабочая площадка**: поддержка LM Studio, постоянные динамические каталоги моделей и импорт внешнего канона, пользовательские Base URL обложек, более широкий предпросмотр глав и безопасная зона переписывания глав.

**Длинные романы** — создание из брифа: генерация фундамента, замысла глав, контекстных пакетов, прозы, рецензии, правок и сверки состояния. Контекст управляется слоями protected / compressible, чтобы длинные книги оставались управляемыми.

**Прогноз сюжета (Narrative forecast)** — перед написанием следующей главы генерируются 2-5 изолированных будущих ветвей от текущего канона, и их главы-такты, решения персонажей, прогнозируемые изменения, риски и соответствие замыслу автора сравниваются прямо в Studio Chat. Выбор ветви записывает только `selected-branch-plan.md`; проза,大纲 и каноническое состояние не меняются. Прогнозы помечаются устаревшими при изменении канона.

**InkOS Short** — Studio Chat и CLI могут создать полный пакет самостоятельного короткого рассказа: полный рукописный текст, записи структуры, записи рецензии, синопсис, продающие точки, промпт обложки и, при настроенном провайдере, изображение обложки.

**InkOS Play** — построение открытых миров или ветвящегося интерактивного fiction из контракта мира на естественном языке: течение времени, агентные персонажи, инвентарь, улики, отношения, состояние сцены, визуальные правила, управляемый выбор, свободные действия и необязательная генерация изображений.

**Интерактивное кино/игры** — превращение идеи, сценария или прозы-референса во ветвящиеся сцены, переменные, концовки, промпты изображений, изображения узлов и экспортируемый пакет проекта.

**Studio Chat** — постоянная чат-поверхность для ответов на вопросы, предложений действий, создания книг, запуска Short / Play, генерации обложек и редактирования текстовых артефактов — без притворства, что действие成功了, до того как существует результат инструмента.

**Agent Skills и исследования** — добавляйте стандартные пакеты `SKILL.md` в `.agents/skills/` или другую директорию AgentSkills, принудительно активируйте через `@skill-id` или запрашивайте веб-исследование для генерации Markdown-отчёта со ссылками на источники.

## Быстрый старт

### Установка

Требуется **Node.js 22 или новее**.

```bash
npm i -g @actalk/inkos
```

### Использование через OpenClaw 🦞

InkOS опубликован как Skill для [OpenClaw](https://clawhub.ai/narcooo/inkos), вызываемый любым совместимым агентом (Claude Code, OpenClaw и т.д.):

```bash
clawhub install inkos          # Установка из ClawHub
```

Если вы установили через npm или склонировали репозиторий, `skills/SKILL.md` уже включён — 🦞 может читать его напрямую без отдельной установки из ClawHub.

После установки Claw должен предпочитать общую точку входа взаимодействия:

```bash
inkos interact --json --message "continue the current book, but keep the pacing tighter"
```

Это проходит через тот же исполнитель диалогов, что использует TUI проекта, так что OpenClaw, TUI и Studio остаются на одном «управляющем мозге». Текущий JSON-вывод содержит текст ответа ассистента и сессию взаимодействия; реальное завершение по-прежнему следует выводить из результатов инструментов и файлов, а не из прозаических утверждений.

Атомарные команды (`plan chapter` / `compose chapter` / `draft` / `audit` / `revise` / `write next`) по-прежнему доступны, но теперь это низкоуровневые инструменты, а не предпочтительная точка входа OpenClaw. Также можно найти его в [ClawHub](https://clawhub.ai), поискав `inkos`.

### Agent Skills

InkOS напрямую использует стандартный формат `SKILL.md` и более не поддерживает отдельный InkOS-специфичный протокол скиллов. Skill даёт Chat Agent профессиональное руководство и статические референсы, но не дополнительные права на выполнение. Создание, написание, редактирование и генерация изображений по-прежнему проходят через инструменты InkOS и шлюзы подтверждения.

Как их использовать:

- Используйте стандартные расположения AgentSkills / OpenClaw: проектные `skills/` и `.agents/skills/`, плюс `~/.agents/skills/` и `~/.openclaw/skills/`. Studio может импортировать полную папку с `SKILL.md` и его статическими референсами; проектный импорт сохраняется в `.agents/skills/`.
- Или задайте `INKOS_SKILL_DIRS=/abs/path/to/skills`; путь может указывать на один каталог скилла или каталог с несколькими подкаталогами скиллов. Для нескольких путей используйте разделитель путей платформы.
- Принудительно активируйте на один ход через `@skill-id`, например: `@detective-play create an evidence-chain open world`.
- Без `@skill-id` Chat Agent сам решает по текущему намерению пользователя, вызывать ли `use_skill`. Виды сессий, фразы-триггеры и совпадение подстрок больше не активируют скиллы.
- Внешние скиллы предоставляют только инструкции и статические референсы. InkOS никогда не автозапускает их скрипты, и скилл не может обойти существующие права инструментов или шлюзы подтверждения.
- Настройка промптов — не скилл. Встроенные пакеты промптов редактируются отдельно в **Project Settings → Prompt packs**, с проектными переопределениями в `prompt/<pack>/<prompt>.md`.

Минимальный `SKILL.md`:

```md
---
name: Detective Play
description: Detective evidence and suspect-board play.
---
Use evidence chains; do not turn clues into generic atmosphere.
```

### Настройка

InkOS разделяет два пути конфигурации: **Studio использует визуальные настройки сервисов**, а **CLI / демон / деплой по-прежнему могут использовать env-переопределения**. Они не молча перезаписывают друг друга.

**Вариант 1: Настройки сервисов Studio (рекомендуется для локального написания)**

```bash
inkos init my-novel
cd my-novel
inkos
```

Откройте Studio и перейдите в **Model Settings**:

1. Выберите сервис: Google Gemini, Moonshot, MiniMax, DeepSeek, kkaiapi, OpenRouter или пользовательский эндпоинт.
2. Вставьте API-ключ и проверьте подключение.
3. Выберите доступную модель и сохраните.
4. Вернитесь в Studio Chat или страницу книги.

Studio использует проектные настройки сервисов и `.inkos/secrets.json`. Он может показывать подсказки о детекте env, но env-файлы не переопределяют выбранный в Studio сервис/модель/Base URL/API-ключ.

MiniMax использует официальный OpenAI-совместимый эндпоинт `/v1/chat/completions`. InkOS по умолчанию отключает возвращаемое размышление для `MiniMax-M3*`; размышление M2.x не может быть отключено на стороне провайдера.

**Вариант 2: env-настройка CLI / демона / деплоя**

```bash
inkos config set-global \
  --lang en \
  --provider <openai|anthropic|custom> \
  --base-url <API endpoint> \
  --api-key <your API key> \
  --model <model name>

# provider: openai / anthropic / custom (используйте custom для OpenAI-совместимых прокси)
# base-url: URL вашего API-провайдера
# api-key: ваш API-ключ
# model: имя вашей модели
```

`--lang en` задаёт английский как язык написания по умолчанию для CLI / демон-запусков. Сохраняется в `~/.inkos/.env`. Для русского языка используйте `--lang ru`.

Также можно вручную отредактировать глобальный `~/.inkos/.env` или проектный `.env`:

```bash
# Обязательно
INKOS_LLM_PROVIDER=                               # openai / anthropic / custom (custom — для любого OpenAI-совместимого API)
INKOS_LLM_BASE_URL=                               # эндпоинт API
INKOS_LLM_API_KEY=                                 # API-ключ
INKOS_LLM_MODEL=                                   # имя модели

# Язык (по умолчанию — глобальная настройка или жанровое значение по умолчанию)
# INKOS_DEFAULT_LANGUAGE=ru                       # zh, en или ru

# Необязательно
# INKOS_LLM_TEMPERATURE=0.7                       # температура
# INKOS_LLM_THINKING_BUDGET=0                      # бюджет расширенного мышления Anthropic
```

Разрешение в CLI начинается от настроек сервисов Studio/проекта, затем наслаивает секреты сервисов, глобальный env, проектный env, env процесса и флаги CLI. Это значит, что CLI может переиспользовать сервис, настроенный в Studio, тогда как env и флаги командной строки остаются явными переопределениями.

**Вариант 3: Мульти-модельный роутинг (необязательно)**

Назначайте разные модели разным агентам — балансируйте качество и стоимость:

```bash
# Назначьте разные модели/провайдеры разным агентам
inkos config set-model writer <model> --provider <provider> --base-url <url> --api-key-env <ENV_VAR>
inkos config set-model auditor <model> --provider <provider>
inkos config show-models        # Посмотреть текущий роутинг
```

Агенты без явного переопределения откатываются к глобальной модели.

**Диагностика конфигурации**

```bash
inkos doctor
```

`doctor` печатает текущий действующий режим конфигурации, откуда взяты сервис / модель / API-ключ, и выполняет проверку подключения к API. Основные режимы:

| Режим | Смысл |
|------|---------|
| `studio-project` | Runtime Studio: используются только настройки Studio/проекта и секреты |
| `cli-project` | Runtime CLI: настройки Studio как база, поверх — env и флаги CLI |
| `legacy-env` | Режим старого env: совместимость со старыми проектами только с `.env` |

Если тест сервиса не проходит, сначала проверьте, что сервис, модель и протокол соответствуют друг другу. API-ключи Google Gemini AI Studio работают с OpenAI-совместимым эндпоинтом Gemini; InkOS автоматически отключает параметр OpenAI `store`, который Google не поддерживает. MiniMax по умолчанию использует официальный OpenAI-совместимый эндпоинт `/v1/chat/completions` и предпочитает рабочий нестриминговый транспорт, избегая потоков, которые возвращают usage, но не текст; `MiniMax-M3*` по умолчанию отключает возвращаемое размышление, тогда как размышление M2.x не отключается на стороне провайдера.

### Заметки по LLM-конфигурации

- **Изоляция настроек Studio / CLI**: Studio всегда использует настройки страницы сервисов и `.inkos/secrets.json`; CLI, демон и деплой-среды поддерживают env-переопределения и разовые флаги команд.
- **Таблица возможностей банка провайдеров**: встроенные baseUrl, протоколы, модели и политики совместимости для 15 сервисов — Google Gemini, Moonshot, MiniMax, Zhipu (GLM), Bailian (Alibaba Cloud Model Studio), DeepSeek, SiliconFlow, Volcengine, Tencent Hunyuan, Baidu ERNIE (Wenxin), iFlytek Spark, OpenRouter, kkaiapi, Ollama и CodingPlan.
- **Проверка принадлежности моделей**: несоответствия вроде `--service google --model kimi-k2.5` падают сразу, и запрос никогда не уходит не тому провайдеру.
- **Фикс совместимости Google Gemini**: ключи AI Studio работают напрямую с OpenAI-совместимым эндпоинтом Gemini; InkOS автоматически отключает параметр OpenAI `store`, который Google не поддерживает.
- **Пробинг транспорта MiniMax**: MiniMax / MiniMax CodingPlan используют официальный OpenAI-совместимый вход `/v1` и автоматически выбирают рабочий нестриминговый транспорт, обходя потоки, которые сообщают usage, но возвращают пустое тело.
- **Совместимость со старым env**: старое сочетание `INKOS_LLM_BASE_URL + INKOS_LLM_MODEL + INKOS_LLM_API_KEY` по-прежнему работает в CLI; без `INKOS_LLM_SERVICE` InkOS пытается вывести сервис из baseUrl.

### Текущие точки входа взаимодействия

**Studio Chat + CLI + TUI разделяют одну поверхность выполнения**

- **Studio Chat**: обсуждение, создание книг, запуск Short, генерация обложек, запуск Play и редактирование постоянных файлов — из одной чат-поверхности; тяжёлые действия показывают карточки подтверждения.
- **Точки создания**: длинный роман, короткий рассказ, фанфик, спин-офф, имитация стиля, продолжение, ветвящийся интерактив и открытый мир доступны как первоклассные точки входа Studio.
- **TUI-дашборд**: `inkos tui` открывает полноэкранную терминальную интерфейсу с командами `/new`, `/short`, `/play`, `/cover`, `/write`, `/confirm`, `/cancel` и сессионной `/model <name>`.
- **Точка входа внешних агентов**: `inkos interact --json --message "..."` остаётся структурированной точкой входа для OpenClaw и других агентов.
- **Атомарные команды на месте**: `plan` / `compose` / `draft` / `audit` / `revise` / `write next` по-прежнему работают для скриптов и продвинутого использования.

### Напишите первую книгу

Английский — значение по умолчанию для английских жанровых профилей; русский — для русских. Выберите жанр и начинайте:

```bash
inkos book create --title "Последний спуск" --genre ru-fantasy     # Фэнтези-роман (по умолчанию на русском)
inkos write next my-book          # Написать следующую главу (полный конвейер: draft → audit → revise)
inkos status                      # Проверить статус
inkos review list my-book         # Посмотреть черновики
inkos review approve-all my-book  # Массовое утверждение
inkos export my-book --format epub  # Экспорт EPUB (читать на телефоне/Kindle)
```

Язык по умолчанию задаётся жанром. Переопределите явно через `--lang en`, `--lang zh` или `--lang ru`. Команда `inkos genre list` показывает все доступные жанры и их языки по умолчанию.

В Studio Chat запросите полный пакет короткого рассказа:

```text

```

```bash

  --direction "modern short fiction marriage reversal evidence-driven heroine" \
  --chapters 12 \
```

### Сгенерируйте самостоятельную обложку

Чтобы сгенерировать только обложку для существующего названия или синопсиса, не запускайте конвейер короткого рассказа. Спросите Studio Chat напрямую:

## Ключевые возможности

### Studio Chat + поверхность действий

Studio Chat — это не просто коробка для вопросов и ответов. Он создаёт длинные книги, запускает Short, генерирует обложки, запускает Play, редактирует постоянные текстовые артефакты и просит подтверждения перед тяжёлыми действиями. Простое обсуждение остаётся простым текстом; явные запросы на создание становятся действиями инструментов.

### InkOS Play: открытые миры и ветвящееся взаимодействие

Play поддерживает постоянное состояние интерактивного мира: персонажи, локации, предметы, улики, отношения, время, текущая сцена, HUD и изображения. Это не захардкоженная RPG-система. Мир культивации может использовать редкость и уровни; романтическая история — эмоциональные стадии; детектив — жизненный цикл улик и достоверность. Правила берутся из контракта мира пользователя и остаются в состоянии мира.

### 37-измеренный аудит + «очищение от AI»

Агент Continuity Auditor проверяет каждый черновик по 37 измерениям: память персонажей, непрерывность ресурсов, закрытие крючков, следование плану, нарративный темп, эмоциональные дуги и многое другое. Встроенная детекция «AI-выдающих» автоматически ловит «голос LLM» — избыточные слова, монотонные паттерны предложений, чрезмерные суммаризации. Цикл написания длинных текстов по умолчанию выполняет не более одной автоматической ревизии; нерешённые критические находки сохраняются в результате для человеческого рассмотрения или последующих команд.

Правила «очищения от AI» встроены в промпты агента Writer: списки слов-выносителей, запрещённые паттерны, инъекция стилистического отпечатка — это снижает AI-следы в источнике. `revise --mode anti-detect` выполняет целевое анти-детекционное переписывание существующих глав.

### Клонирование стиля

`inkos style analyze` исследует референсный текст и извлекает статистический отпечаток (распределение длин предложений, паттерны частотности слов, ритм-профили) плюс читаемый LLM стилистический гид. `inkos style import` вливает этот отпечаток в книгу — все будущие главы принимают стиль, а Reviser аудиторит по нему.

### Креативный бриф

`inkos book create --brief my-ideas.md` — передайте свои заметки мозгового штурма, документ мира или карточки персонажей. Агент Architect строит книгу из вашего брифа (генерируя `story_bible.md` и `book_rules.md`), а не изобретает с нуля, и сохраняет бриф в `story/author_intent.md`, чтобы длиннорочное намерение книги не исчезло после инициализации.

### Панель управления входом

У каждой книги теперь два долговременных Markdown-документа управления:

- `story/author_intent.md`: чем эта книга должна стать в длинной перспективе
- `story/current_focus.md`: на что следующие 1-3 главы должны возвращать внимание

Перед написанием можно выполнить:

```bash
inkos plan chapter my-book --context "Pull attention back to the mentor conflict first"
inkos compose chapter my-book
```

Это генерирует `story/runtime/chapter-XXXX.intent.md`, `context.json`, `rule-stack.yaml` и `trace.json`. `intent.md` — человекочитаемый контракт; остальные — артефакты выполнения/отладки. `plan` вызывает LLM для создания замысла главы; `compose` только компилирует локальные документы и состояние, поэтому его можно выполнить, не закончив настройку API-ключа.

### Управление длиной

`draft`, `write next` и `revise` теперь разделяют один консервативный регулятор длины:

- `--words` задаёт целевой коридор, а не жёсткое точное обещание
- Китайские главы по умолчанию `zh_chars`; английские — `en_words`; русские — `en_words` (подсчёт слов)
- Если глава уходит из мягкого коридора, InkOS может выполнить один корректирующий прогон нормализации (сжатие или расширение), а не жёстко резать прозу
- Если после этого прогона глава всё ещё вне жёсткого диапазона, InkOS сохраняет её, но показывает видимое предупреждение о длине и телеметрию в результате и индексе глав

### Написание продолжения

`inkos import chapters` импортирует существующий текст романа и перестраивает структурированное состояние, сводки глав, крючки, отношения персонажей и читаемые Markdown-проекции. Поддерживаются `Глава N` / `Chapter N` / `第 N 章`, пользовательские паттерны разбиения и возобновляемый импорт. После импорта `inkos write next` может продолжить историю.

### Фанфик

`inkos fanfic init --from source.txt --mode canon` создаёт фанфик-книгу из исходного материала. Четыре режима: canon (верное продолжение), au (альтернативная вселенная), ooc (out of character), cp (ship-ориентированный). Включает импорт канона, фанфик-специфичные измерения аудита и контроль информационных границ, чтобы сохранять согласованность lore.

### Мульти-модельный роутинг

Разные агенты могут использовать разные модели и провайдеры. Writer на Claude (сильнее в творчестве), Auditor на GPT-4o (дешевле и быстрее), Radar на локальной модели (нулевая стоимость). `inkos config set-model` настраивает по агентам; ненастроенные агенты откатываются к глобальной модели.

### Демон-режим + уведомления

`inkos up` запускает автономный фоновый цикл, пишущий главы по расписанию. Конвейер продолжается через обрабатываемые некритические проблемы и ставится на паузу с просматриваемым результатом, когда нужно человеческое суждение. Уведомления через Telegram, Feishu (Lark), WeCom (Enterprise WeChat) и Webhook (HMAC-SHA256-подпись + фильтрация событий). Логи в `inkos.log` (JSON Lines), `-q` — тихий режим.

### Совместимость с локальными моделями

Поддерживается любой OpenAI-совместимый эндпоинт (`--provider custom`). Авто-откат стрима — когда SSE не поддерживается, InkOS автоматически повторяет в синхронном режиме. Откатной парсер обрабатывает нештатный вывод малых моделей, а восстановление частичного контента срабатывает при обрыве потока.

### Надёжность

Каждая глава создаёт автоматический снапшот состояния — `inkos write rewrite` откатывает любую главу к состоянию до написания. Writer выводит предписательный чек-лист (область контекста, ресурсы, ожидающие крючки, риски) и таблицу посленаписания; Auditor кросс-валидирует обе. Файловая блокировка предотвращает конкурентное написание. Пост-написательный валидатор включает межглавный детектор повторений и десяток жёстких правил с авто-точечным исправлением.

Система крючков использует валидацию схем Zod — `lastAdvancedChapter` должен быть целым числом, `status` может быть только open/progressing/deferred/resolved. JSON-дельты от LLM обрабатываются через `applyRuntimeStateDelta` (неизменяемое обновление) и `validateRuntimeState` (структурная проверка) перед сохранением. Повреждённые данные отклоняются, а не распространяются.

Лимиты вывода моделей управляются карточками моделей провайдеров в банке провайдеров. Зарезервированные ключи в `llm.extra` (max_tokens, temperature, model, messages, stream и т.д.) вырезаются, чтобы предотвратить случайное переопределение ключевых параметров запроса.

## Как это работает

InkOS использует harness pi-agent как общее ядро рассуждения и вызова инструментов. Агент интерпретирует намерение пользователя и выдаёт типизированные действия; хост выполняет детерминированные инструменты, применяет подтверждения и права, управляет состоянием и выводит завершение из реальных файлов и результатов инструментов. Длинные романы, короткие рассказы, сценарии, раскадровки, интерактивное кино, Play и перевод разделяют эту архитектуру, сохраняя собственные Skills, модели состояния и производственные шаги.

  <img src="assets/arch-system.svg" width="900" alt="System architecture">
</p>

Длинные главы производятся несколькими агентами последовательно:

<p align="center">
  <img src="assets/arch-pipeline.svg" width="900" alt="Chapter pipeline">
</p>

| Агент | Ответственность |
|-------|---------------|
| **Radar** | Сканирует тренды платформы и предпочтения читателей, чтобы информировать направление истории (модульный, пропусkabемый) |
| **Planner** | Читает замысел автора + текущий фокус + результаты поиска памяти, создаёт замысел главы (сохранять / избегать) |
| **Composer** | Выбирает релевантный задаче контекст из структурированного состояния, управляющих документов и Markdown-проекций, затем компилирует стек правил и runtime-артефакты |
| **Architect** | Генерирует фундаментальные файлы при создании книги, импорте или настройке спин-оффа: story frame, правила, персонажи и длиннорочные управляющие файлы |
| **Writer** | Производит прозу из скомпонованного контекста (управление длиной, диалоговая驱动) |
| **Observer** | Переизвлекает 9 категорий фактов из текста главы (персонажи, локации, ресурсы, отношения, эмоции, информация, крючки, время, физическое состояние) |
| **Reflector** | Выводит JSON-дельту (не полный markdown); код-слой применяет валидацию схемы Zod, затем неизменяемую запись |
| **Normalizer** | Однократное сжатие/расширение только когда глава явно выходит из жёсткого диапазона длины |
| **Continuity Auditor** | Валидирует черновик против структурированного состояния, управляющих документов и контекста главы |
| **Reviser** | Исправляет критические проблемы, найденные аудитором; цикл написания по умолчанию выполняет не более одной автоматической ревизии и помечает остальное для человеческого рассмотрения |

Если аудит не проходит, конвейер по умолчанию выполняет один проход revise → повторный аудит. Оставшиеся проблемы сохраняются в результате и состоянии для человеческого рассмотрения или последующих команд.

### Долгосрочная память

Каноническая память каждой книги разделена на три слоя:

| Слой | Назначение |
|-------|---------|
| `story/state/*.json` | Авторитетное структурированное состояние: текущее состояние, крючки, сводки глав и связанные runtime-данные, валидированные схемами Zod |
| `story/*.md` | Человекочитаемые проекции: `current_state.md`, `pending_hooks.md`, `chapter_summaries.md`, `character_matrix.md` |
| `story/memory.db` | SQLite временная память на Node 22+, используется для релевантного поиска фактов, крючков и сводок |

Continuity Auditor проверяет черновики против этого состояния. Если персонаж «помнит» то, чего он никогда не видел, или достаёт оружие, потерянное две главы назад, — аудитор это поймает.

Settler более не просит модель выводить полные markdown-файлы. Он производит JSON-дельту, а код-слой применяет и валидирует её неизменяемо перед сохранением. Markdown остаётся читаемой проекцией. Существующие книги мигрируют со старого Markdown при первом прогоне.

На Node 22+ автоматически включается база данных SQLite временной памяти (`story/memory.db`), поддерживающая релевантный поиск исторических фактов, крючков и сводок глав — это предотвращает разрастание контекста от инъекции целых файлов.

### Панель управления и runtime-артефакты

Помимо runtime-состояния, InkOS разделяет ограждения и кастомизацию на просматриваемые управляющие документы:

- `story/author_intent.md`: длиннорочный замысел автора
- `story/current_focus.md`: краткосрочное направление
- `story/runtime/chapter-XXXX.intent.md`: цель главы, список сохранять/избегать, разрешение конфликтов
- `story/runtime/chapter-XXXX.context.json`: фактически выбранный для этой главы контекст
- `story/runtime/chapter-XXXX.rule-stack.yaml`: приоритетные слои и отношения переопределений
- `story/runtime/chapter-XXXX.trace.json`: трассировка компиляции этой главы

Это значит, что брифы, узлы плана, правила книги и текущие запросы больше не сбиваются в один комок промпта; InkOS сначала компилирует, потом пишет.

### Система правил написания

У агента Writer ~25 универсальных правил написания (мастерство персонажей, нарративная техника, логическая согласованность, языковые ограничения, «очищение от AI»), применимых ко всем жанрам.

Плюс у каждого жанра свои правила (запреты, языковые ограничения, темп, измерения аудита), и у каждой книги свои `book_rules.md` (персона протагониста, числовые пределы, кастомные запреты), `story_bible.md` (мир), `author_intent.md` (длиннорочное направление) и `current_focus.md` (краткосрочное направление). `volume_outline.md` по-прежнему служит планом по умолчанию, но в управлении входом v2 оно больше не автоматически переопределяет замысел текущей главы.

## Режимы использования

InkOS предоставляет четыре режима взаимодействия, все они разделяют одни атомарные операции:

### 1. Полный конвейер (одна команда)

```bash
inkos write next my-book              # Draft → аудит → авто-ревизия, всё в одном
inkos write next my-book --count 5    # Написать 5 глав последовательно
```

`write next` по умолчанию использует управляющую цепочку `plan -> compose -> write`. Если нужен старый путь сборки промптов, явно задайте это в `inkos.json`:

```json
{
  "inputGovernanceMode": "legacy"
}
```

По умолчанию теперь `v2`. `legacy` остаётся доступным как явный откат.

### 2. Атомарные команды (композируемые, дружелюбные внешним агентам)

```bash
inkos plan chapter my-book --context "Focus on the mentor conflict first" --json
inkos compose chapter my-book --json
inkos draft my-book --context "Focus on the dungeon boss encounter and party dynamics" --json
inkos audit my-book 31 --json
inkos revise my-book 31 --json
```

Каждая команда независимо выполняет одну операцию. `--json` выводит структурированные данные. `plan` / `compose` управляют входами; `draft` / `audit` / `revise` занимаются прозой и проверками качества. Их можно вызывать из внешних AI-агентов через `exec` или использовать в скриптах.

### 3. Режим агента на естественном языке

```bash
inkos agent "Write a LitRPG novel where the MC is a healer class in a dungeon world"
inkos agent "Write the next chapter, focus on the boss fight and loot distribution"
inkos agent "Create a progression fantasy about a mage who can only use one spell"
```

Режим агента показывает инструменты согласно текущему виду сессии: создание книги, редактирование управляющей панели, планирование, композиция, написание, аудит, ревизия, Short, обложка и инструменты Play доступны только там, где они имеют смысл. Рекомендуемый поток агента: сначала подстроить управляющую панель, затем `plan` / `compose`, затем выбрать написание только черновика или полный конвейер.

### 4. Режим Play в Studio

Точки входа Studio **Open World** и **Branching Interactive** запускают интерактивное создание без предварительного создания книги. Опишите, как работает мир, как течёт время, действуют ли персонажи как агенты и что значат предметы/улики. InkOS запишет результат в локальное состояние мира, чтобы сессию можно было продолжить.

## CLI-справочник

| Команда | Описание |
|---------|-------------|
| `inkos init [name]` | Инициализировать проект (без имени — текущий каталог) |
| `inkos book create` | Создать книгу (`--genre`, `--chapter-words`, `--target-chapters`, `--brief <file>`, `--lang zh/en/ru`) |
| `inkos book update [id]` | Обновить настройки книги (`--chapter-words`, `--target-chapters`, `--status`, `--lang`) |
| `inkos book list` | Список всех книг |
| `inkos book delete <id>` | Удалить книгу и все её данные (`--force` — без подтверждения) |
| `inkos genre list/show/copy/create` | Просмотр, копирование или создание жанров |
| `inkos plan chapter [id]` | Сгенерировать `intent.md` следующей главы (`--context` / `--context-file` для текущего направления) |
| `inkos compose chapter [id]` | Сгенерировать `context.json`, `rule-stack.yaml` и `trace.json` следующей главы |
| `inkos write next [id]` | Полный конвейер: написать следующую главу (`--words` для переопределения, `--count` для батча, `-q` тихий режим) |
| `inkos write rewrite [id] <n>` | Переписать главу N (восстановление снапшота состояния, `--force` — без подтверждения) |
| `inkos draft [id]` | Только черновик (`--words` для переопределения объёма, `-q` тихий режим) |
| `inkos audit [id] [n]` | Аудит конкретной главы |
| `inkos revise [id] [n]` | Ревизия конкретной главы |
| `inkos agent <instruction>` | Режим агента на естественном языке |
| `inkos review list [id]` | Посмотреть черновики |
| `inkos review approve-all [id]` | Массовое утверждение |
| `inkos status [id]` | Статус проекта |
| `inkos export [id]` | Экспорт книги (`--format txt/md/epub`, `--output <path>`, `--approved-only`) |
| `inkos radar scan` | Скан рыночных/трендовых входов для направления новой книги |
| `inkos fanfic init` | Создать фанфик-книгу из исходного материала (`--from`, `--mode canon/au/ooc/cp`) |
| `inkos short run` | Сгенерировать пакет самостоятельного короткого рассказа |
| `inkos eval [id]` | Сгенерировать отчёт о качестве (`--json`, диапазоны глав) |
| `inkos consolidate [id]` | Консолидировать сводки глав для управления контекстом длинной книги |
| `inkos forecast create/show/select` | Создать, перепроверить и выбрать неканонические длинные ветви; выбор сохраняет только кандидат-план |
| `inkos interact` | Точка входа для внешних агентов / CLI на естественном языке (`--json`, `--message`, `--book`) |
| `inkos config set-global` | Задать глобальный CLI / демон / деплой LLM env-конфиг (`~/.inkos/.env`) |
| `inkos config show-global` | Показать глобальный конфиг |
| `inkos config set/show` | Посмотреть или обновить проектный конфиг |
| `inkos config set-model <agent> <model>` | Переопределение модели по агентам (`--base-url`, `--provider`, `--api-key-env`) |
| `inkos config remove-model <agent>` | Убрать переопределение модели агента (откат к дефолту) |
| `inkos config show-models` | Показать текущий роутинг моделей |
| `inkos doctor` | Диагностика (тест подключения API + подсказки совместимости провайдеров) |
| `inkos detect [id] [n]` | AIGC-детекция (`--all` — все главы, `--stats` — статистика) |
| `inkos style analyze <file>` | Анализ референсного текста для извлечения стилистического отпечатка |
| `inkos style import <file> [id]` | Импорт стилистического отпечатка в книгу |
| `inkos import canon [id] --from <parent>` | Импорт канона родителя в спин-офф-книгу |
| `inkos import chapters [id] --from <path>` | Импорт существующих глав для продолжения (`--split`, `--resume-from`) |
| `inkos analytics [id]` / `inkos stats [id]` | Аналитика книги (процент прохождения аудита, основные проблемы, рейтинг глав, расход токенов) |
| `inkos update` | Обновить до последней версии |
| `inkos` / `inkos studio` | Запустить веб-площадку (`-p` для порта, по умолчанию 4567) |
| `inkos tui` | Запустить полноэкранную терминальную TUI |
| `inkos up / down` | Запустить/остановить демон (`-q` тихий режим, авто-запись `inkos.log`) |

`[id]` определяется автоматически, если в проекте только одна книга. Все команды поддерживают `--json` для структурированного вывода. `draft` / `write next` / `plan chapter` / `compose chapter` принимают `--context` для направления, а `--words` переопределяет целевой объём главы. `book create` поддерживает `--brief <file>` для передачи креативного брифа — Architect строит из ваших идей, а не генерирует с нуля. `plan chapter` вызывает LLM для создания замысла главы; `compose chapter` не требует живого LLM, поэтому управляемые входы можно посмотреть, не закончив настройку API.

CLI также принимает разовые флаги LLM-переопределения во время выполнения: `--service`, `--model`, `--api-key-env`, `--base-url`, `--api-format <chat|responses>`, `--stream`, `--no-stream`. Например:

```bash
inkos write next --service google --model gemini-2.5-flash
inkos up --service moonshot --model kimi-k2.5 --api-key-env MOONSHOT_API_KEY
```
